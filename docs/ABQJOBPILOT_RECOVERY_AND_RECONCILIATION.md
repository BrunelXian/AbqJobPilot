# Runtime Recovery and Reconciliation (Run 004)

AbqJobPilot recovery is a local, human-approved correction of application metadata. It does not run, resume, terminate, or validate Abaqus. The normal dashboard and the five read-only MCP tools remain unchanged.

## Ownership and classification

`runtime/queue.json` is current control state. `runtime/live_status.json` is the runner's last observation. `<Project>/project.db` is durable historical projection, not a queue controller. `runner_owner.json` and the OS lock are distinct from a solver process. `assess_runtime()` reports `CLEAN`, `ACTIVE_RUNNER`, `STALE_RUNNING`, `RECOVERY_REQUIRED`, or `UNCONFIRMED`. A historical `RUNNING` row, existing ODB, or absent `.lck` does not prove a currently running or completed analysis.

## Read-only plan

`build_recovery_plan(runtime_dir, project_db=None)` does not create locks or a database. Its `RecoveryPlan` has `runtime_dir`, optional `project_db`, `assessment`, `fingerprint`, `process_fingerprint`, `affected_queue_ids`, `transitions`, `warnings`, `unresolved`, `can_apply`, and deterministic `plan_id`; `to_dict()` and `to_json()` are available. The fingerprints cover queue/live bytes, ownership metadata, process observations, and relevant artifact/database file signatures. Solver files are stat'ed, never opened. No plan is applied just by opening the dialog.

If `project.db` exists, recovery checks its schema read-only and refuses to run a migration as a side effect. An active SQLite WAL contributes to the plan fingerprint; a changed WAL invalidates prior approval.

The only supported queue transition is `RUNNING` / `DATACHECK_RUNNING` / `FULL_RUNNING` to raw `UNKNOWN_INTERRUPTED`. This is not a failure or completion verdict. The corresponding stale live observation can become `IDLE`. For this narrow candidate, queue ID, phase, and start time must match, and live telemetry must contain the integer return code written after the managed command exited. Run 005 additionally requires matching runtime/queue/phase process identity and `CONFIRMED_EXITED` evidence for the tracked launcher and an observed solver-candidate child. There must be no active/unconfirmed runner owner, no `.lck`, no conflicting terminal SQLite/report evidence, and a successful auxiliary Windows process listing with no recognized Abaqus process. Missing lineage, identity mismatch, active descendants, malformed metadata, or missing exit telemetry block the change. ODB presence or timestamp never qualifies a job for completion. Process enumeration remains point-in-time evidence; if uncertain, investigate manually.

## Local approval and apply

Use **Tools > Runtime Recovery**. Review the report, refresh it, or copy it. Apply is disabled unless the plan has a supported transition and no unresolved risk. The local confirmation names the runtime and exact queue IDs, and states that no solver or engineering files will be changed. Confirmation creates a short-lived, single-use token bound to the plan ID; this is internal GUI code, not a public API, CLI, or MCP operation.

Apply acquires the existing `queue_transaction` lock, rechecks runner ownership, process identity, and process listing, rebuilds the plan, and requires the same metadata/process fingerprints and plan ID. It writes a `PREPARED` audit record in `runtime/recovery_audit/<operation-id>.json`, then uses `queue_store.save_queue` and the existing atomic JSON writer. If an existing formal `project.db` belongs to that runtime, it projects only the affected queue record with `sync_records(..., provenance="runtime_recovery")`. It never initializes a missing database during assessment or apply. The audit records runtime, timestamp, queue IDs, previous/new statuses, both fingerprints, approval source `local_gui_confirmation`, outcome, and errors. Project archive metadata mode includes these JSON audit records, while transient `.queue.lock`, `.runner.lock`, and `runner_owner.json` are excluded by the existing archive policy.

Queue JSON, live JSON, audit JSON, and SQLite do **not** share a single transaction. A failure after queue replacement can leave queue `UNKNOWN_INTERRUPTED` and live status still running. The operation returns `PARTIAL_OR_FAILED` and attempts to finalize its audit record; a fresh assessment can propose the remaining live-only correction. If SQLite projection fails after both JSON files are corrected, a new plan may propose **only** the affected historical projection when the same queue ID has nonterminal history and the live observation points to a valid prior locally approved `PARTIAL_OR_FAILED` audit. It requires fresh confirmation and cannot create a second Run for the same `queue_id`. A failed final audit write can leave a `PREPARED` record, which must be treated as incomplete evidence and does not authorize a history-only retry. Never delete a `.lck`, ODB, INP, CAE, STA, MSG, DAT, or LOG to make the display look clean.

Repeated approved recovery cannot create duplicate Runs: the SQLite repository matches `queue_id` and preserves existing terminal Run evidence. Legacy provenance is not replaced on an existing Job/Run. Read-only assessment reports SQLite disagreements; stronger terminal historical evidence blocks correction. A historical terminal Run is not downgraded to `UNKNOWN`.

The recovery workflow is deliberately absent from the public Automation Surface and MCP. The five MCP tools remain `abq_preflight`, `abq_list_jobs`, `abq_job_status`, `abq_locate_outputs`, and `abq_prepare_enqueue`. No unattended `recovery apply` exists.
